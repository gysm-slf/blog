# 网络请求

**axios**: 在浏览器环境中基于 **`XMLHttpRequest` (XHR)** 实现。XHR 不支持获取响应流，只能在整个响应接收完成后一次性获得完整数据（虽然可以通过 `onprogress` 事件获取已接收的片段，但无法像流式那样按块控制读取，且不能用于流式解析如 SSE）。

**fetch**:  是现代浏览器和 Node.js 中内置的全局函数，用于发送 HTTP 请求。基于 Promise 设计，语法简洁，用于替代传统的 `XMLHttpRequest`。
- **默认不带 Cookie**：需要设置 `credentials: 'include'` 才会发送同源或跨域 Cookie。

::: tip 提示
XMLHttpRequest、fetch、axios、http(s)包的关系：

- **XMLHttpRequest** 和 **fetch** 是浏览器原生提供的 API，两者是并列关系。
- **axios** 是一个跨环境的第三方库，在浏览器中封装 `XMLHttpRequest`，在 Node.js 中封装 `http` 模块。
- Node.js 的 **`http` 模块** 是该环境中最基础的请求工具。
  :::

```text
浏览器环境                     Node.js 环境
─────────────────────────────────────────────────
高层 API:
  fetch (标准Promise)          fetch (Node 18+，基于undici)
  XMLHttpRequest (回调)         (无此API)
         ↓                           ↓
中层实现:                       undici库
  浏览器内部网络栈                    ↓
  (C++实现，不暴露JS)          http/https模块 (核心)
                                    ↓
底层基础:                        net/tls模块
  TCP Socket + TLS                 ↓
                              操作系统Socket API
```

| 功能                | Axios                                      | Fetch                                   | 说明                                              |
|-------------------|--------------------------------------------|-----------------------------------------|-------------------------------------------------|
| **请求/响应拦截器**      | ✅ 内置                                       | ❌ 需手动封装                                 | Axios 可以全局或实例拦截请求和响应                            |
| **自动 JSON 转换**    | ✅ 自动                                       | ❌ 需手动 `.json()`                         | Axios 自动将对象转为 JSON 发送，并自动解析 JSON 响应             |
| **错误处理**          | 网络错误或 HTTP 状态码非 2xx 时 reject               | 仅网络故障时 reject，HTTP 错误码需手动判断             | Fetch 需要检查 `response.ok`                        |
| **超时设置**          | ✅ `timeout` 配置                             | ❌ 需借助 `AbortController` + `setTimeout`  | Axios 原生支持超时，Fetch 需手动实现                        |
| **取消请求**          | ✅ `AbortController` + `CancelToken`        | ✅ `AbortController`                     | 两者均支持现代 AbortController，Axios 还保留旧版 CancelToken |
| **上传进度**          | ✅ `onUploadProgress` 回调                    | ❌ 需自行封装（通过 `ReadableStream` 计算）         | Axios 基于 XHR 原生支持，Fetch 需复杂实现                   |
| **下载进度**          | ✅ `onDownloadProgress`                     | ❌ 需自行封装（通过流式读取计算）                       | 同上                                              |
| **并发请求**          | ✅ `axios.all` / `axios.spread`             | ✅ `Promise.all`                         | Axios 提供辅助方法，但本质仍是 Promise                      |
| **请求/响应数据转换**     | ✅ `transformRequest` / `transformResponse` | ❌ 需手动处理                                 | Axios 允许在请求发出前或响应到达后自动转换数据                      |
| **实例化配置**         | ✅ 可创建独立实例，统一配置                             | ❌ 需每次手动设置或封装函数                          | Axios 的实例化非常方便                                  |
| **默认携带 Cookies**  | 浏览器中默认携带同域 Cookies                         | 需设置 `credentials: 'include'`            | Fetch 默认不带 Cookie，更安全但需手动开启                     |
| **跨域请求**          | 支持 CORS，默认行为与 XHR 一致                       | 支持 CORS，但对某些限制更严格（如不允许跨域携带 Cookie 除非配置） | 两者均需服务器配合                                       |
| **HTTP/2 推送支持**   | 依赖浏览器环境                                    | 依赖浏览器环境                                 | 无本质区别                                           |
| **流式响应**          | ❌ 不支持（XHR 无法获取流）                           | ✅ 通过 `response.body.getReader()` 实现     | **Fetch 的独家能力**，适合大模型逐字输出、SSE 等场景               |
| **服务端渲染（SSR）**    | 良好支持（如 Next.js 的 Axios 实例）                 | 需注意 Node.js 环境下的 fetch 实现（可能缺少部分功能）     | Axios 在 SSR 中更稳定                                |
| **TypeScript 支持** | 优秀，类型定义完善                                  | 较好，但 Response 类型需自行定义                   | Axios 类型更友好                                     |


## axios 拦截器示例

axios.js

```js
import axios from 'axios'
// 创建 axios 实例
const service = axios.create({
  baseURL: process.env.VUE_APP_API_BASE_URL || 'https://jsonplaceholder.typicode.com',
  timeout: 10000
})
// 请求拦截器
service.interceptors.request.use(
  config => {
    // 可以在这里添加 token 等
    // config.headers['Authorization'] = 'Bearer ' + getToken()
    return config
  },
  error => {
    return Promise.reject(error)
  }
)
// 响应拦截器
service.interceptors.response.use(
  response => {
    // 对响应数据做点什么
    return response.data
  },
  error => {
    // 对响应错误做点什么
    console.error('请求错误:', error)
    return Promise.reject(error)
  }
)
export default service
```

## http(s) 请求示例

```js
const http = require('http');
const https = require('https');

function request(options, data = null) {
  const lib = options.protocol === 'https:' ? https : http;
  return new Promise((resolve, reject) => {
    const req = lib.request(options, (res) => {
      const chunks = [];
      res.on('data', chunk => chunks.push(chunk));
      res.on('end', () => {
        const body = Buffer.concat(chunks).toString();
        resolve({ statusCode: res.statusCode, headers: res.headers, body });
      });
    });
    req.on('error', reject);
    if (data) req.write(data);
    req.end();
  });
}
// get
const url = require('url');

// 目标 URL（带查询参数）
const targetUrl = 'https://api.example.com/users?id=123&active=true';

const parsedUrl = new url.URL(targetUrl);

const options = {
  protocol: parsedUrl.protocol, // 协议类型，如http、https
  hostname: parsedUrl.hostname,
  port: parsedUrl.port || (parsedUrl.protocol === 'https:' ? 443 : 80),
  path: parsedUrl.pathname + parsedUrl.search,
  method: 'GET',
  headers: {
    'Accept': 'application/json'
  }
};

request(options).then(response => {
  console.log('状态码:', response.statusCode);
  console.log('响应体:', response.body);
}).catch(err => {
  console.error('请求失败:', err.message);
});

//post
const postData = {
  name: '张三',
  age: 25,
  email: 'zhangsan@example.com'
};

const jsonData = JSON.stringify(postData);

const parsedUrl = new url.URL('https://api.example.com/users');

const options = {
  protocol: parsedUrl.protocol, // 协议类型，如http、https
  hostname: parsedUrl.hostname,
  port: parsedUrl.port || 443,
  path: parsedUrl.pathname,
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Content-Length': Buffer.byteLength(jsonData)
  }
};

request(options, jsonData).then(response => {
  console.log('状态码:', response.statusCode);
  console.log('响应:', response.body);
});
```

## 跨域

### 简介

浏览器出于安全考虑，遵循 **同源策略（Same-Origin Policy）**。  

- 若请求的目标 URL 与当前页面源不同，即为**跨域请求**。
- 跨域请求默认会被浏览器拦截（但请求其实已经发到服务器，只是浏览器拒绝返回结果给页面脚本）。

::: warning 提示
浏览器认为 **协议 + 域名 + 端口** 三者完全相同才算同源
:::

| 当前页面 | 目标地址 | 是否同源 |
|---|---|---|
| `https://a.com` | `https://a.com/api` | ✅ 同源 |
| `https://a.com` | `http://a.com` | ❌ 协议不同 |
| `https://a.com` | `https://b.com` | ❌ 域名不同 |
| `https://a.com:8080` | `https://a.com` | ❌ 端口不同 |

> 同源策略限制了什么

默认情况下，跨源发起的请求：

- 响应能回来，但**浏览器会拦截**，JS 读不到数据
- **默认不携带 Cookie / 凭据**
- 某些请求头不能自定义发送

> CORS 本质

CORS（Cross-Origin Resource Sharing）是 W3C 标准，本质是 **服务器通过响应头告诉浏览器"哪些源、哪些方法、哪些头、能不能带凭据"**。它是服务器的"授权声明"，不是前端的开关。

> "源 origin" 和 "站 site"

- **Origin（源）** = scheme + host + port。跨源 = host / port / scheme 任一不同。
- **Site（站）** = scheme + 注册域(eTLD+1)。跨站只看注册域和 scheme。

→ **关键结论：跨源 ≠ 跨站。**
例：页面 `https://app.example.com` 调用接口 `https://api.example.com`
- 跨源 ✅（host 不同 app.example.com !== api.example.com）
- 同站 ✅（注册域都是 example.com【注册于：公共后缀.com + 前一级example。再往前属于子域计算同站时会忽略】，scheme 都是 https）
  → 在 SameSite 眼里这是**同站**，`Lax`/`Strict` 都会正常带 Cookie。很多人栽在这个误区上。

### 带凭据的跨域请求

跨域默认不带 Cookie，想带必须**前后端同时配合**。

#### 前端：显式声明"我要带凭据"

```js
// fetch
fetch('https://api.b.com/user', {
  credentials: 'include'   // 关键
});

// XMLHttpRequest
const xhr = new XMLHttpRequest();
xhr.withCredentials = true; // 关键
```

#### 后端：必须响应两个头

```
Access-Control-Allow-Origin: https://a.com   # 注意：不能是 *
Access-Control-Allow-Credentials: true       # 关键
```

⚠️ **致命细节**：只要 `Allow-Credentials: true`，`Access-Control-Allow-Origin` **就必须写成具体的源**，写成 `*` 浏览器会直接拒绝。这是规范硬性要求。

#### 浏览器侧 Cookie 自身限制


即使上面都配好，Cookie 能否发送还受自身属性影响：

- `SameSite`

| 取值 | 含义 | 同站请求 | 跨站·顶级导航(点击链接/302跳转) | 跨站·子请求(fetch/XHR/iframe/img/POST) |
|---|---|---|---|---|
| `None` | 不做站点隔离，任意跨站都带 | ✅ | ✅ | ✅（必须配 `Secure`） |
| `Lax`（默认） | 宽松：允许"安全的"跨站跳转带 | ✅ | ✅ | ❌ |
| `Strict` | 严格：仅同站 | ✅ | ❌ | ❌ |

- `Secure`：是否开启加密，若开启则仅当请求地址为 `https` 时才允许（不是开启就带还要看跨域等其它配置）携带 `Cookie`。
- `Domin`：
- `HttpOnly`：不影响发送，但 JS 读不到

### OPTIONS 预检请求（Preflight）

#### 1. 简单请求（不触发 OPTIONS）

同时满足：

- 方法为 `GET` / `HEAD` / `POST`
- 请求头仅限：`Accept`、`Accept-Language`、`Content-Language`、`Content-Type`
- `Content-Type` 仅限：`application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`
- 没有 `ReadableStream` 等

简单请求直接发，服务器回应 `Access-Control-Allow-Origin` 即可。

#### 2. 非简单请求或跨域请求 → 触发 OPTIONS 预检

> 如果请求方法是复杂请求或者`跨域请求`，浏览器在发送请求之前会先发一次 `OPTIONS` 预检请求问服务器"我能不能这么干"，得到许可后才发真正的请求。

以下任一情况都会触发预检：

- 方法为 `PUT` / `DELETE` / `PATCH` 等
- `Content-Type` 是 `application/json`
- 自定义请求头（如 `Authorization`、`X-Token`）
- 带凭据（`credentials: include`）且带自定义头等组合场景
- 跨域

> 实战中最常见的触发点：**`Content-Type: application/json`** 和 **自定义认证头**。

#### 3. 预检过程（浏览器自动完成）

第 1 步 —— 浏览器发 OPTIONS 询问：

```
OPTIONS /user HTTP/1.1
Origin: https://a.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

第 2 步 —— 服务器回许可：

```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://a.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400
```

第 3 步 —— 预检通过后，浏览器才发真正的请求（此时才带 Cookie 和真实 body）。

#### 4. 关键响应头含义

| 响应头 | 作用 |
|---|---|
| `Access-Control-Allow-Origin` | 允许访问的源，`*` 或具体源 |
| `Access-Control-Allow-Methods` | 允许的 HTTP 方法 |
| `Access-Control-Allow-Headers` | 允许携带的请求头 |
| `Access-Control-Allow-Credentials` | 是否允许带 Cookie |
| `Access-Control-Max-Age` | 预检结果缓存秒数，期间不再发 OPTIONS |

### 常见配置示例

#### Nginx

```nginx
location /api/ {
    add_header 'Access-Control-Allow-Origin' 'https://a.com' always;
    add_header 'Access-Control-Allow-Credentials' 'true' always;
    add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, OPTIONS' always;
    add_header 'Access-Control-Allow-Headers' 'content-type, authorization' always;

    if ($request_method = 'OPTIONS') {
        add_header 'Access-Control-Max-Age' 86400;
        return 204;
    }
}
```

#### Node / Express

```js
const cors = require('cors');
app.use(cors({
  origin: 'https://a.com',   // 具体源，勿用 '*'
  credentials: true,
  methods: ['GET','POST','PUT','DELETE','OPTIONS'],
  allowedHeaders: ['content-type','authorization'],
  maxAge: 86400
}));
```

#### Spring Boot

```java
@Configuration
public class CorsConfig {
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/**")
                        .allowedOrigins("https://a.com") // 具体源
                        .allowCredentials(true)
                        .allowedMethods("GET","POST","PUT","DELETE","OPTIONS")
                        .allowedHeaders("content-type","authorization");
            }
        };
    }
}
```

### 最容易踩的坑（速查）

- ❌ 带 Cookie 时后端 `Allow-Origin` 写成 `*` → 浏览器直接拒绝。
- ❌ 前端忘了 `credentials: 'include'` → Cookie 始终不带。
- ❌ Cookie 是 `SameSite=Lax/Strict` 且非 HTTPS → 跨站带不出去。
- ✅ `Access-Control-Allow-Origin` 需要动态回显请求里的 `Origin` 时，记得校验白名单，别无脑回显。

::: danger 注意
发送请求：浏览器自动在请求头（Cookie）中携带该域下的有效 Cookie 发给后端（需满足同源或CORS跨域携带条件）。

写入/设置：后端通过响应头（Set-Cookie）返回指令，浏览器内核自动接收并写入本地存储（按域名、路径、有效期进行管理）。 
:::

## promise

```js
/** promise 的三种状态：
      - pending：等待状态，比如正在进行网络请求，或者定时器没有到时间。
      - fulfill：满足状态，当我们主动回调了resolve时，就处于该状态，并且会回调.then()
      - reject：拒绝状态，当我们主动回调了reject时，就处于该状态，并且会回调.catch()
*/
new Promise((resolve, reject) => {
	setTimeout(() => {  
	  resolve(3)  
	}, 3000)
}).then(response => { //该函数实际为调用resolve函数
	console.log(response) // 3
}).catch(error => { //该函数实际为调用reject函数
	console.log(error) 
})
// 第二种写法
new Promise((resolve, reject) => {
	setTimeout(() => {
	  resolve(3)  
	}, 3000)
}).then(response => {	console.log(response) }, error => { console.log(error) })
```

## `async` 和 `await`

### `await` 跟 -> promise 的函数 
```js
/** 
 * Tips: 
  - async函数完全可以看作多个异步操作，包装成的一个 Promise 对象，而await命令就是内部then命令的语法糖。
  - await后面的promise运行结果可能是rejected，最好把await放入try{}catch{}中
	- Await后的异步操作，如果彼此没有依赖关系最好同时触发，在下面场景一会有介绍
	- Await只能在async函数之中，如果在普通函数中，会报错
 */

/** 
 * async/await 异步函数
特点：
  1: 必须成对出现
  2: async为函数关键字, 以此关键词修饰函数后则自动将常规函数转换成Promise，返回值也是一个Promise对象（注意若函数未返回promise实例，会转换为promise后立即resolve进行返回，resolve值即为函数返回值）
  3: await后面跟着的必须是一个promise对象, 且会等待promise状态更新后才会执行后续代码 如果不是则会被转成Promise对象。
  4: await后面的代码都会被阻塞 
 */
const getValueA = () => {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      console.log("A")
      resolve(2)
    }, 2000)
  })
}
const getValueB = () => {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      console.log("B")
      resolve(4)
    }, 4000)
  })
}
const getValueC = () => {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      console.log("C")
      resolve(3)
    }, 3000)
  })
}
const getValueABC = async () => {
  // 方法一：执行完毕需要2 + 4 + 3为9秒 ABC均为同步顺序执行  
  const A = await getValueA()  // 只有getValueABC函数内部await后面代码会阻塞, 调用处后面会直接执行 正如修饰符所描述一样 调用了一个异步方法getValueABC
  console.log(A) // 2  
  /** 
   * A.then is not a function 当 await promise 不写.then时会直接返回响应值（前提已变为满足状态否则依然为promise对象）, 
   * 且.then会在resolve(后立刻执行) 在后续代码用变量执行.then是无效的，且await又是等待promise变为满足状态（调用resolve）
   * 或调用拒绝状态（调用reject）后的同步代码，因此A.then一定是报错undefined;只有pending状态变为满足状态之前才可以调用.then 
   * 如果已经变为了满足状态则.then为undefined
   * */
  A.then(response => console.log(response)) 
  await getValueA().then(response => console.log(response)) // 如果需要请直接写.then
  const B = await getValueB()
  const C = await getValueC()
  return A * B * C
```

### `await` 的特殊性

::: code-group

```js [片段1]
var a = function () {
  setTimeout(() => {console.log('异步执行了')}, 3000)
};
var b = async function () {
  await a(); // 将 a() 转换为 promise 然后执行 a 函数内部同步代码，执行到最后的隐式 return undefined 或遇到 await 则交出控制权，此时继续调用方（b）后续的同步代码
  console.log('下面的代码执行了')
};
b()
// 输出结果为： 
// 下面的代码执行了 
// 异步执行了 
```

```js [片段2]
var a = function () {
  return new Promise(resolve => {
    setTimeout(() => {
      console.log('异步执行了');
      resolve(['11111'])
    }, 3000)
  })
};
var b = async function () {
  await a();
  console.log('下面的代码执行了')
};
b()
// 输出结果为： 
// 异步执行了 
// 下面的代码执行了 
```

:::

::: tip
如何理解这一现象？

导致这一现象是因为await需要基于Promise进行操作否则会失效，

若async形容的函数未返回promise对象会被隐式处理为Promise(resolve(函数的返回值)), 在代码1中返回的即undefined
:::

### 多次请求的数据对齐

> 以下代码段1和2是否会出现file与response对应错位问题？

```js
// 代码段1
for (const file of files) {
  promises.push(
    this.handleFileUpload(file).then((response) => {
      response.file = {
        name: file.name,
        mimetype: file.type,
      };
    })
  );
}
// 代码段2
for (var i = 0; i < files.length; i++) {
  var file = files[i];
  promises.push(
          handleFileUpload(file).then(function(response) {
            console.log(file.name);
          })
  );
}
```

::: danger
只有代码段2会出现问题，问题发生的核心原因就是代码段2引用的均为同一个变量file，

而代码段1每一次file相当于重新定义赋值，可以理解为定义了五个变量（只不过每次都是同名，会覆盖掉）
:::
